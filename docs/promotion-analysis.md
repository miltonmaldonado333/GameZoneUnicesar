# Promotion Module Analysis

**1. The three promotions have different calculation rules but share common attributes and behaviors. How is this reflected in the class hierarchy design? What OOP mechanism allows each promotion type to calculate its discount differently without the rest of the system having to know the concrete types?**

This is reflected by creating an abstract base class named `Promotion` that encapsulates the common attributes (identifier, name, start date, end date) and shared behaviors[cite: 7]. The three specific types (`PercentageDiscount`, `CategoryDiscount`, and `BulkPurchaseDiscount`) extend this base class[cite: 7]. The Object-Oriented Programming (OOP) mechanism that allows this is **Polymorphism** (specifically, method overriding). It allows the `SaleService` to interact with a general `Promotion` object and invoke its discount calculation method; the Java runtime will automatically execute the specific logic of the concrete promotion class without the system needing to evaluate its exact type.

**2. The base class Promotion cannot implement the discount calculation method because each type has different logic. How is this method declared in the base class and what does this declaration guarantee regarding subclasses?**

The method is declared as an `abstract` method within the `Promotion` base class, specifically as `abstract double calculateDiscount(Sale sale);`[cite: 7]. This declaration guarantees a strict contract: all concrete subclasses extending `Promotion` are forced to provide their own specific implementation of this method[cite: 7]. If a subclass fails to implement it, the Java compiler will throw an error, ensuring that every promotion type in the system knows how to calculate its own discount.

**3. The business rule states that only the promotion with the highest discount is applied. In which class is this selection logic located and why is this location consistent with the layered architecture principle? Why should this logic NOT be in the Sale class or in the console menu?**

This selection logic is located in the `PromotionService` class, specifically within the `findBestPromotionFor(Sale sale)` method[cite: 7]. This is consistent with the layered architecture principle because the Service layer is entirely responsible for implementing and orchestrating business rules[cite: 5, 7]. This logic should NOT be in the `Sale` class because the Model layer should only represent data entities and their internal state, not handle complex comparative logic or manage lists of external promotions[cite: 5]. Furthermore, it must NOT be in the console menu (`GameZoneUI`) because the UI layer's sole responsibility is capturing inputs and displaying outputs; placing business logic there violates the separation of concerns[cite: 5].

**4. What modifications are necessary in the Sale class and in the generateReceipt method so that the receipt shows the applied discount? Do these modifications break any existing behavior in the system?**

The `Sale` class must be modified by adding two new private attributes: `appliedPromotionName` (String) and `discountAmount` (double), along with their respective getters and setters[cite: 7]. Additionally, the `generateReceipt` method must be updated to display the subtotal, the applied discount amount (including the promotion name), and the final calculated total (subtotal minus discount)[cite: 7]. These additive modifications do not break the existing behavior of the system[cite: 7]. If no promotion is applicable to a sale, the discount amount remains zero, the promotion name remains null or empty, and the final total calculation processes exactly as it did before[cite: 7].

**5. Active promotions are determined by comparing the current date with the start and end dates of each promotion. Where is this validation performed (in the Promotion class, in the PromotionService, or both)? Justify.**

The validation is performed cooperatively in **both** classes, respecting their specific responsibilities. The `Promotion` model class contains a boolean method `isActive(LocalDate date)` which encapsulates the specific internal logic of comparing a given date against its own start and end date attributes[cite: 7]. Meanwhile, the `PromotionService` class uses this method to filter the overall repository list and retrieve only the active promotions (e.g., inside `listActivePromotions()`)[cite: 7]. This perfectly justifies the layered architecture: the model knows _how_ to check its own state, and the service orchestrates _when_ and _why_ to check it across multiple objects.
